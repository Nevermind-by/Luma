# Руководство по разработке

Luma находится в активной разработке. На текущем этапе приоритет — корректность, понятная архитектура и возможность безопасно проверять каждое изменение.

## Перед изменением

Перед началом работы:

1. прочитайте [README.md](README.md);
2. при изменении архитектуры сверяйтесь с [ARCHITECTURE.md](ARCHITECTURE.md);
3. определите, какой слой действительно должен измениться;
4. проверьте существующие тесты и близкие сценарии.

## Принцип небольших изменений

Изменение должно решать одну понятную задачу.

Предпочтительный цикл:

```text
задача
  ↓
ветка
  ↓
изменение
  ↓
тест
  ↓
Pull Request
  ↓
CI
  ↓
main
  ↓
следующая задача
```

Не объединяйте в одном Pull Request несвязанные исправления только ради уменьшения количества PR.

Несколько связанных коммитов внутри одной ветки — нормально. Важнее целостность задачи, а не искусственное ограничение числа коммитов.

## Архитектура

Ядро не должно зависеть от конкретного сайта или способа распространения.

Для нового источника используйте `UpdateSource`. Для нового сценария установки не добавляйте низкоуровневую логику в SwiftUI.

Подробные правила находятся в [ARCHITECTURE.md](ARCHITECTURE.md).

## Тесты

Новая нетривиальная логика должна сопровождаться тестами.

Особенно важно тестировать:

- сравнение версий;
- разбор внешних данных;
- сопоставление приложения с источником;
- сохранение и восстановление состояния;
- загрузку и отмену;
- установку и откат;
- работу с cookies и границами домена.

Перед отправкой Pull Request желательно локально выполнить сборку и тесты схемы `Luma`.

## Работа с безопасностью

Не добавляйте в репозиторий:

- пароли;
- токены;
- cookies;
- приватные ключи;
- файлы с персональными учётными данными;
- загруженные установщики и локальное состояние конкретного Mac.

Нельзя отключать Gatekeeper, quarantine или другие системные механизмы безопасности ради упрощения сценария.

## Коммиты

Сообщение коммита должно кратко описывать сделанное изменение.

Пример:

```text
Добавить обработку отмены загрузки
```

Предпочтительны атомарные коммиты, которые можно независимо проверить или откатить.

Не требуется создавать новый коммит ради каждого отдельного файла. Несколько связанных изменений можно объединить в один коммит, если они относятся к одной задаче.

## Ветки

Ветки используются для изоляции задач. `main` содержит интегрированное состояние проекта и не используется как рабочая ветка.

Для каждой отдельной задачи создавайте короткоживущую ветку от актуального `main`.

Рекомендуемые префиксы:

```text
feature/   новая функциональность
fix/       исправление ошибки
refactor/  изменение внутренней структуры без изменения поведения
test/      тесты и тестовая инфраструктура
docs/      документация
chore/     технические и служебные изменения
```

Примеры:

```text
feature/localization
fix/cookie-domain-matching
refactor/update-coordinator
test/localization-ui
docs/release-process
chore/git-workflow
```

Имя ветки должно кратко описывать задачу. Не используйте даты, номера машин или слишком общие названия вроде `work` или `changes`.

### Порядок работы

```text
main
  │
  └── feature/<задача>
          │
          ├── коммит
          ├── коммит
          └── коммит
                 │
                 ▼
           Pull Request
                 │
                 ▼
                CI
                 │
                 ▼
            merge в main
                 │
                 ▼
        удалить рабочую ветку
```

Правила:

1. Не пушьте рабочие изменения напрямую в `main`.
2. Перед созданием ветки начинайте от последнего актуального `main`.
3. В одной ветке держите одну логическую задачу.
4. После завершения создавайте Pull Request в `main`.
5. Перед merge проверяйте изменения, тесты и результат CI.
6. После merge удаляйте ветку, если она больше не нужна.
7. Не делайте force-push в `main`.

Для небольших задач используется та же схема. Небольшой размер изменения не является причиной обходить ветки и Pull Request.

## Pull Request

Pull Request должен содержать:

- что изменено;
- зачем это изменено;
- какие сценарии проверены;
- какие ограничения остались.

Если изменение затрагивает пользовательский интерфейс, приложите скриншот или кратко опишите новый сценарий.

Предпочтительный способ слияния — **Squash and merge**. Он оставляет в `main` историю на уровне завершённых задач, а промежуточные рабочие коммиты остаются внутри Pull Request.

## CI

CI запускается для Pull Request в `main` и для изменений, попадающих в `main`.

Push в рабочую ветку используется для публикации промежуточной работы, но рабочая ветка не считается интегрированной, пока Pull Request не прошёл проверки.

Тяжёлые Release-процессы не должны запускаться на каждый рабочий коммит.

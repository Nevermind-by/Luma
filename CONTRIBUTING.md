# Руководство по разработке

Luma находится в активной разработке. На текущем этапе приоритет — корректность, понятная архитектура и возможность безопасно проверять каждое изменение.

## Перед изменением

Перед началом работы:

1. прочитайте [`README.md`](README.md);
2. при изменении архитектуры сверяйтесь с [`ARCHITECTURE.md`](ARCHITECTURE.md);
3. определите, какой слой действительно должен измениться;
4. проверьте существующие тесты и близкие сценарии.

## Принцип небольших изменений

Изменение должно решать одну понятную задачу.

Предпочтительный цикл:

```text
задача
  ↓
изменение
  ↓
тест
  ↓
CI
  ↓
следующая задача
```

Не объединяйте в одном изменении несвязанные исправления только ради уменьшения количества коммитов.

## Архитектура

Ядро не должно зависеть от конкретного сайта или способа распространения.

Для нового источника используйте `UpdateSource`. Для нового сценария установки не добавляйте низкоуровневую логику в SwiftUI.

Подробные правила находятся в [`ARCHITECTURE.md`](ARCHITECTURE.md).

## Тесты

Новая нетривиальная логика должна сопровождаться тестами.

Особенно важно тестировать:

- сравнение версий;
- разбор внешних данных;
- сопоставление приложения с источником;
- сохранение и восстановление состояния;
- загрузку и отмену;
- установку и откат;
- работу с cookies и границами домена.

Перед отправкой изменения желательно локально выполнить сборку и тесты схемы `Luma`.

## Работа с безопасностью

Не добавляйте в репозиторий:

- пароли;
- токены;
- cookies;
- приватные ключи;
- файлы с персональными учётными данными;
- загруженные установщики и локальное состояние конкретного Mac.

Нельзя отключать Gatekeeper, quarantine или другие системные механизмы безопасности ради упрощения сценария.

## Коммиты

Сообщение коммита должно кратко описывать сделанное изменение.

Пример:

```text
Добавить обработку отмены загрузки
```

Предпочтительны атомарные коммиты, которые можно независимо проверить или откатить.

## Ветки и Pull Request

Для заметных изменений используйте отдельную короткоживущую ветку и Pull Request.

Описание Pull Request должно содержать:

- что изменено;
- зачем это изменено;
- какие сценарии проверены;
- какие ограничения остались.

Если изменение затрагивает пользовательский интерфейс, приложите скриншот или кратко опишите новый сценарий.

## Документация
